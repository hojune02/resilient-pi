
# Day 8 — Metrics Specification

**Project:** Resilient Pi  
**Component:** Observable C++ HTTP server  
**Telemetry backend:** Prometheus  
**Visualization:** Grafana

## 1. Purpose

This document defines each metric, its semantics, type, unit, diagnostic purpose, and known limitations.

Metrics are intended to answer operational questions, not merely display activity.

The observability design separates:

1. Service-level symptoms
2. Dependency state
3. Resource utilization
4. Monitoring-system health

## 2. Application Metrics

### 2.1 HTTP Request Count

**Name:** `resilient_http_requests_total`  
**Type:** Counter  
**Unit:** Requests

**Meaning**

Counts HTTP response attempts generated by the application.

**Question answered**

How many requests has the server attempted to answer since startup?

**PromQL**

```promql
rate(resilient_http_requests_total[1m])
```

**Limitations**

- Counter resets when the application restarts.
- Includes `/metrics` scrapes.
- Connections that close without a response may not be counted.
- Does not guarantee that clients received the response.
- Does not distinguish individual routes.

### 2.2 HTTP Error Count

**Name:** `resilient_http_errors_total`  
**Type:** Counter  
**Unit:** HTTP error responses

**Meaning**

Counts generated responses with HTTP status 400 or above.

**Question answered**

Are requests producing errors?

**PromQL**

```promql
rate(resilient_http_errors_total[1m])
```

**Limitations**

- Includes both 4xx and 5xx errors.
- A deliberate 404 increases the counter even if the application is functioning correctly.
- Does not identify the route or error reason.
- Does not include every possible network-level failure.

A future revision may separate client errors from server errors using fixed status-class labels.

### 2.3 HTTP Send Failures

**Name:** `resilient_http_send_failures_total`  
**Type:** Counter  
**Unit:** Failed response transmissions

**Meaning**

Counts failed attempts to send complete HTTP response buffers to a socket.

**Question answered**

Is the server encountering response-transmission errors?

**PromQL**

```promql
increase(resilient_http_send_failures_total[5m])
```

**Limitations**

A successful `send()` only confirms that bytes were accepted by the local kernel.

It does not prove delivery to the remote application.

### 2.4 HTTP Request Duration

**Name:** `resilient_http_request_duration_seconds`  
**Type:** Histogram  
**Unit:** Seconds

**Meaning**

Measures elapsed time from successful `accept()` to completion of the application's request-handling path.

It includes:

- Receiving the request
- Application processing
- Database operations when applicable
- Response transmission attempts

It excludes time spent waiting in the kernel listen backlog.

**Question answered**

How long does the server take to handle accepted connections?

**PromQL — p95**

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(resilient_http_request_duration_seconds_bucket[1m])
  )
)
```

**PromQL — mean**

```promql
rate(resilient_http_request_duration_seconds_sum[1m])
/
rate(resilient_http_request_duration_seconds_count[1m])
```

**Limitations**

- Histogram percentile values are estimates.
- Fixed bucket boundaries constrain resolution.
- Sparse traffic can make short-window percentile estimates unstable.
- The histogram population can include connections that do not produce an HTTP response.
- Metrics scrapes contribute to the measurements.

### 2.5 Active HTTP Connections

**Name:** `resilient_http_active_connections`  
**Type:** Gauge  
**Unit:** Connections

**Meaning**

Counts accepted connections currently being handled by the application.

**Question answered**

How many accepted sockets are actively being processed?

**PromQL**

```promql
resilient_http_active_connections
```

**Limitations**

The server is single-threaded, so the value is normally zero or one.

A `/metrics` scrape observes its own active connection, commonly producing a value of one.

It does not count connections waiting in the kernel accept backlog.

It is not a measure of total concurrent client demand.

### 2.6 Process Uptime

**Name:** `resilient_process_uptime_seconds`  
**Type:** Gauge  
**Unit:** Seconds

**Meaning**

Elapsed monotonic-clock time since the observable server's metrics instance was initialized.

**Question answered**

How long has the current application instance been running?

**PromQL**

```promql
resilient_process_uptime_seconds
```

**Limitations**

Uptime resets after application restart.

A process being alive does not imply database readiness.

### 2.7 Database Connection State

**Name:** `resilient_db_connection_up`  
**Type:** Gauge  
**Unit:** Boolean-like value

Values:

```text
1 = last observed database check was successful
0 = last observed database check failed
```

**Meaning**

Represents the application's most recently observed database state.

**Question answered**

Was PostgreSQL usable at the last relevant check?

**PromQL**

```promql
resilient_db_connection_up
```

**Limitations**

- Not a continuously refreshed independent probe.
- May become stale if no database operation or readiness check occurs.
- Does not measure replication status, data correctness or overall database performance.
- May reflect connection status rather than a successful SQL round trip when updated from the `/counter` path.

### 2.8 Database Operation Duration

**Name:** `resilient_db_operation_duration_seconds`  
**Type:** Histogram  
**Unit:** Seconds

**Meaning**

Measures application-side duration of database-backed operations.

The measured interval can include:

- Database connection checks
- Reconnection attempts
- SQL execution
- Transaction execution

**Question answered**

Are application database operations becoming slower?

**PromQL — p95**

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(resilient_db_operation_duration_seconds_bucket[1m])
  )
)
```

**Limitations**

- Not equivalent to PostgreSQL server-side query execution time.
- Includes reconnection behavior.
- Currently recorded for `/counter` and `/counter/increment`, not necessarily `/ready`.
- Sparse traffic reduces histogram reliability.

## 3. Host Metrics

These metrics are provided by Prometheus Node Exporter.

### 3.1 Host CPU Utilization

**Source metric:** `node_cpu_seconds_total`  
**Type:** Counter  
**Unit:** CPU-seconds

**Derived utilization**

```promql
100 * (
  1 -
  avg(
    rate(node_cpu_seconds_total{mode="idle"}[1m])
  )
)
```

**Question answered**

How busy are the host's CPU cores?

**Limitations**

- Host-wide, not C++ process-specific.
- Includes PostgreSQL, Grafana, Prometheus and other processes.
- Depends on the measurement window.
- CPU saturation is not required for user-visible failures.

### 3.2 Available Host Memory

**Name:** `node_memory_MemAvailable_bytes`  
**Type:** Gauge  
**Unit:** Bytes

**Question answered**

How much memory does Linux estimate is available for new workloads without swapping?

**PromQL**

```promql
node_memory_MemAvailable_bytes
```

**Limitations**

- Host-wide, not process-specific.
- Includes kernel estimates about reclaimable memory.
- Does not identify the process responsible for memory pressure.

### 3.3 Total Host Memory

**Name:** `node_memory_MemTotal_bytes`  
**Type:** Gauge  
**Unit:** Bytes

**Meaning**

Physical memory reported by Linux.

**PromQL**

```promql
node_memory_MemTotal_bytes
```

### 3.4 One-Minute Load Average

**Name:** `node_load1`  
**Type:** Gauge  
**Unit:** Load average

**Meaning**

Average number of runnable or uninterruptible tasks over approximately one minute.

**PromQL**

```promql
node_load1
```

**Limitations**

Load average is not equivalent to CPU utilization.

Tasks waiting in uninterruptible sleep can contribute.

It should be interpreted relative to the machine's core count and workload.

## 4. Monitoring-System Metrics

### 4.1 Scrape Success

**Name:** `up`  
**Type:** Gauge  
**Unit:** Boolean-like value

**Meaning**

Prometheus reports whether the latest scrape of a target succeeded.

**PromQL**

```promql
up{job="resilient-pi"}
```

```promql
up{job="node"}
```

**Interpretation**

```text
1 = latest target scrape succeeded
0 = latest target scrape failed
```

**Important distinction**

`up = 1` does not imply that application requests are successful.

Prometheus can scrape `/metrics` while PostgreSQL is unavailable.

If Prometheus itself is stopped, it cannot produce new `up` samples.

A missing series is not equivalent to `up = 0`.

## 5. Metric Types

### Counter

A cumulative measurement that normally increases until the process resets.

Examples:

```text
resilient_http_requests_total
resilient_http_errors_total
```

Use rates or increases to interpret activity over time.

### Gauge

A measurement that may increase or decrease.

Examples:

```text
resilient_http_active_connections
resilient_db_connection_up
node_memory_MemAvailable_bytes
```

### Histogram

A distribution represented by cumulative buckets, total count and total sum.

Example:

```text
resilient_http_request_duration_seconds_bucket
resilient_http_request_duration_seconds_sum
resilient_http_request_duration_seconds_count
```

Histograms allow approximate quantile estimation across aggregated observations.

## 6. Service Symptoms vs Resource Indicators

| Metric | Classification | Interpretation |
|---|---|---|
| HTTP error rate | Service symptom | Requests are failing |
| HTTP latency | Service symptom | Requests are slow |
| Request throughput | Service activity | Traffic volume and completion rate |
| DB connection state | Dependency indicator | Database availability |
| DB operation latency | Dependency symptom | Application database operations are slow |
| Host CPU utilization | Resource indicator | CPU activity |
| Available host memory | Resource indicator | Memory headroom |
| Active connections | Application state | Accepted sockets currently handled |
| Prometheus `up` | Monitoring indicator | Latest scrape result |

Metrics showing user-visible symptoms should be investigated before assuming a resource-related root cause.

For example, a PostgreSQL outage can produce HTTP 503 responses while host CPU utilization remains low.

## 7. Cardinality Policy

A Prometheus time series is identified by its metric name and label set.

High-cardinality labels can create large numbers of distinct time series.

Potentially dangerous labels include:

```text
user_id
request_id
trace_id
raw_url
client_ip
session_id
sql_query
```

For example:

```text
http_requests_total{user_id="123456"}
```

can generate a separate time series for every user.

### Current policy

Application metrics use fixed names and no per-request identifying labels.

A future version may introduce bounded labels such as:

```text
method = GET | POST
route = /health | /ready | /counter | /counter/increment | other
status_class = 2xx | 4xx | 5xx
```

These labels have small, controlled value sets.

Raw user-controlled paths should not be used as labels.

## 8. Logging Policy

When a request fails, structured logs should ideally include:

- Timestamp
- Severity
- Stable error category
- Bounded route identifier
- HTTP method
- HTTP status
- Elapsed duration
- Database connection or operation state when relevant
- A correlation identifier, when available and safe

Avoid logging:

- Passwords
- Authentication tokens
- Session cookies
- Authorization headers
- Secrets in environment variables
- Database credentials
- Unnecessary personal information
- Complete raw request bodies
- Arbitrary SQL parameter values

Logs should provide diagnostic context without becoming a repository of sensitive data.

## 9. Observability Overhead

Observed C++ process RSS:

```text
Persistent server: 7848 KiB
Observable server: 7952 KiB
Difference:          104 KiB
```

Observed monitoring stack cgroup memory:

```text
Prometheus:     65.76 MiB
Node Exporter:   9.64 MiB
Grafana:       458.15 MiB
Combined:      533.55 MiB
```

A six-round sequential HTTP benchmark recorded:

```text
Persistent mean: 2.175 ms
Observable mean: 2.022 ms
```

The experiment did not resolve a clear latency penalty caused by instrumentation.

The results do not prove that instrumentation is free or improves performance.

The monitoring stack's measured memory footprint is materially larger than the observed application RSS difference.

## 10. Known Limitations

1. Instrumentation executes inside the single-threaded HTTP application.
2. Metrics scraping contributes to application traffic.
3. Active connections are difficult to interpret under this architecture.
4. Database state is last-observed rather than continuously probed.
5. Histogram values can be misleading under sparse traffic.
6. Process CPU is not exported as an application time series.
7. Request count and latency sample count may differ.
8. Error metrics do not distinguish client errors from server errors.
9. Monitoring outages can produce gaps in historical telemetry.
10. No alerting rules have been configured.

## 11. Future Improvements

- Add fixed route and status-class labels.
- Separate HTTP 4xx and 5xx error rates.
- Add a bounded active-request or pending-connection metric.
- Track process CPU and RSS through a process exporter or direct instrumentation.
- Add explicit readiness probe scheduling.
- Measure telemetry overhead with repeated controlled experiments.
- Add alerting on elevated error rates and database unavailability.
- Consider off-device Prometheus/Grafana deployment.
- Reassess metric thread safety when adopting a multithreaded HTTP architecture.
